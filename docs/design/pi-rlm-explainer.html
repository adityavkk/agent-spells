System explainer · proposed design

pi-rlm turns a large problem into an inspectable program

Instead of putting an entire repository into one prompt, a controller receives a map of the material, writes small JavaScript cells, and spends a shared budget on the exact slices, models, agents, or recursive frames it needs.

TL;DR. The large input stays outside model context. A typed RlmProgram tells the runtime what goes in and what must come out. Model-authored JavaScript performs the adaptive search. Every host effect crosses a broker that authorizes, budgets, records, and can replay it.
Problem
Long inputs lose quality before they exceed the context window.
Approach
Keep data host-side; let a controller inspect and recursively query selected parts.
Tradeoff
More runtime machinery, latency, schemas, migrations, and failure modes.
Recommendation
Build the safe recursive core first; add opaque Pi agents only after approval and replay work.

The mental model: map, not cargo

Imagine a repository as cargo too large for one model request. Normal prompting loads the cargo into the model. pi-rlm gives the controller a variable catalog: names, types, descriptions, constraints, sizes, hashes, and bounded previews. The full values remain in snapshots.

A 300,000-token repository starts an RLM run. What enters the controller's first request?

Reveal the answer

Descriptors and bounded previews. Full values stay in immutable host snapshots. The controller requests slices explicitly, which makes context growth observable and enforceable.

The model chooses what to inspect next. The runtime decides whether that choice is legal, affordable, durable, and replayable.

Root controller: what it generates, where it runs

The root controller uses a one-response Pi model driver. It does not execute repository code or host tools itself. It generates a concise rationale and one JavaScript cell. rlm_eval sends that cell to a fresh QuickJS context. Any model, agent, recursion, artifact, or tool operation must cross the host bridge broker.

Step by step: from root tool call to final answer

These snippets follow messages 4 through 30 in the sequence. Only the JavaScript string executes in QuickJS. The surrounding tool envelope belongs to the controller protocol.

1 · Root emits one rlm_eval tool call messages 4–5

The model returns structured tool arguments. The rationale becomes trajectory metadata. The code becomes the next guest cell.

Generated by the root controller. Not executed inside the controller model process.

2 · QuickJS executes deterministic structure and plain model fan-out messages 6–12

Chunking and coverage are code. Semantic judgment goes to plain model calls. The broker reserves the uncached batch before it launches any item.

Executed in the root frame's QuickJS worker. Each llm.batch() item executes through the Pi model runtime, not inside QuickJS.

3 · Generated code may invoke a full Pi agent messages 13–16

Use agent() when the task needs an independent, tool-using Pi agent. Version 1 requests per-run approval because delegation cannot prove the child's effective capabilities.

This fresh cell reopens context handles and reads JSON results from workspace. The broker then adapts the call to pi-subagents/delegation; the reviewer runs outside QuickJS.

4 · Generated code may recurse into a child RLM frame messages 17–22

Use recurse() when one difficult slice benefits from another inspect, code, and query loop. The child gets a new controller session and worker, but not a new budget.

This fresh cell reconstructs its locals from workspace. The coordinator creates a child frame that repeats the controller-to-QuickJS sequence with smaller context handles.

5 · Root commits typed output with answer() messages 23–30

After every required route has a result or explicit failure, the root emits a final cell. Free text cannot finish the run.

The broker validates the declared JSON Schemas, commits the final payload and event, then returns only typed output, usage, and artifact references to the caller.

A complete trajectory: contract to final output

This illustrative run reviews eight changed route chunks. The root begins with plain calls, escalates one uncertain result to a full agent, recurses on one failed chunk, asks a final adversarial agent to check the merge, makes one recoverable output mistake, and then commits a valid answer. Generated cells can differ between runs; the runtime contracts do not.

Prompt examples and the RLM programs they imply

These are modeled after Anthropic's dynamic workflow examples, but adapted to pi-rlm. Claude workflows primarily spawn full agents. pi-rlm first decides whether each stage needs a plain llm(), a full agent(), or another recurse() frame.

i
Explicit start. pi-rlm has no magic workflow keyword. Say “use pi-rlm” or call /rlm. The host records a single-use launch grant before the parent agent may call rlm_run; an unsolicited model call cannot start a run.
1 · ScopeName the files, logs, sessions, or documents that form the input.
2 · Harness shapeAsk for fan-out, adversarial checks, a tournament, or a loop.
3 · Stop ruleDefine coverage, evidence, tests, or “no new findings” as completion.
4 · AuthorityState read-only versus edits, commands, network, and approvals.
5 · BudgetSet call, time, token, depth, and concurrency limits.
6 · OutputName the structured result and evidence required from every item.
!
Current contract limitation. RlmProgram selects a predeclared profile but has no per-run numeric limit field. Budget phrases such as “48 calls” therefore require a matching trusted profile. A future narrowing-only limits override would make prompt-to-program compilation more faithful without allowing a project prompt to widen policy.
competing hypotheses + loopFlaky test root-cause investigation
Use pi-rlm to investigate auth-refresh.test.ts, which fails about once in 50 runs. Read the test, implementation, and captured CI logs. Generate at least four competing race-condition hypotheses from independent evidence. Try to refute each one. Stop when one theory survives two independent checks, or report that the evidence budget was exhausted. Stay read-only. Limit the run to 48 calls, 20 minutes, and concurrency 6.

Representative RlmProgram

  • inputs: test, implementation, ciLogs
  • outputs: hypotheses[], winningTheory, evidence[], reproductionPlan, stopReason
  • profile: root-cause-readonly
  • limits: calls 48, 20 minutes, concurrency 6

Generated controller shape

  • llm.batch() creates hypotheses from disjoint log and code slices.
  • One verifier call tries to refute each hypothesis.
  • recurse() investigates only the surviving difficult slice.
  • A bounded loop stops on evidence agreement or budget exhaustion.
discover + parallel edit + verifyRepository-wide model rename
Use pi-rlm to rename the User domain model to Account everywhere. First discover definitions, serialized names, database mappings, imports, tests, and docs. Group edits so files do not conflict. Give each group to an isolated worker, then have a separate reviewer check every patch against the migration rubric. Run targeted checks after each group and the full suite at the end. Do not merge a group that fails verification. Require approval before edits and commands.

Representative RlmProgram

  • inputs: repository, migrationRules
  • outputs: changeGroups[], verification[], remainingUses[], testSummary
  • profile: migration-review
  • capabilities: opaque workers, worktrees, test commands

Generated controller shape

  • Code and inputs.repository.grep(...) build a complete occurrence inventory.
  • agent({ agent: "worker", ... }) prepares one non-overlapping patch group.
  • agent({ agent: "reviewer", ... }) adversarially checks each patch group.
  • A broker-authorized mutation step promotes only verified groups and reports residual occurrences.

This is a Phase 3 target, not executable by the current version 1 contract as written: AgentSpec does not yet expose worktree or merge controls. Agent and command capabilities require approval, and promotion needs a future explicit allowlisted broker operation.

Patterns adapted from Anthropic's official dynamic workflows guide and “A harness for every task”: fan-out and synthesize, adversarial verification, generate and filter, tournaments, migrations, and loop-until-done investigations.

Trace one run from question to answer

A route-security review shows why the runtime needs both model judgment and deterministic code.

Compile the program contract program/compiler.ts

The compiler validates names and JSON Schemas, resolves one profile, snapshots the matching route files, creates descriptors, and rejects collisions before model spend.

Controller inspects structure controller.ts

The first request contains instructions, descriptors, budget, DSL declarations, and a bounded trajectory. The controller writes a small cell to chunk route handlers by file.

One batch covers every route dsl/llm-batch.ts

llm.batch() validates all item keys and atomically reserves uncached work. If preflight fails, nothing launches and no call or attempt is consumed.

Code reduces semantic results interpreter/quickjs.ts

The model calls judge authorization semantics. JavaScript performs coverage checks, joins duplicates, and identifies any file without a result.

Typed answer commits persistence/journal.ts

answer({ findings }) must satisfy the declared schema. The payload is written and hashed before its commit event. Only the final result and artifact references return to the parent conversation.

The rule worth remembering

Atomic rejection is a safety feature, not a partial failure.

If a batch cannot reserve the whole uncached group, no item launches and the rejected preflight consumes zero calls and attempts. Cache hits consume neither.

Replay changes what “state” means

A normal REPL can keep arbitrary objects in memory. pi-rlm cannot if a run must survive a process crash. Each cell receives a fresh context and a reconstructed, typed workspace. Closures, module state, timers, and prototype mutations are not durable state.

ConcernDesign ruleWhy
Large inputImmutable content snapshotsResume sees the original bytes even if project files change.
Cross-cell valuesJSON plus tagged handles in workspaceSerializable, bounded, and replayable.
Model and agent effectsStable keys and committed resultsCompleted read-only calls replay without spending again.
Crash during mutationunknown_effectThe runtime refuses to pretend exactly-once behavior.
QuickJS isolationCapability boundary, not OS sandboxWorker, WASM, or runtime vulnerabilities can still matter.
!
Opaque agents need approval every run. Delegation v1 cannot prove effective tools, mutation access, extensions, or network authority. “Do not edit” is guidance, not enforcement.

DSPy supplied abstractions, not the whole production runtime

DSPy's first-party RLM is unusually strong prior art: typed signatures, variable descriptors, interpreter ownership, ordered batched model calls, immutable history, typed submission, and fallback extraction. It is still experimental and is not the paper's reference implementation.

Glossary
Variable space
Host-backed values plus model-facing descriptors and previews. Separate from prompt token space.
Workspace
Serializable cross-cell state: JSON and tagged context or artifact handles.
Trajectory
Immutable per-iteration rationale, code, output preview, full reference, and typed error.
Unknown effect
A mutating call may have happened remotely, but no durable result was committed.
Fallback extractor
A separately versioned model call that tries to produce typed output after controller exhaustion.
