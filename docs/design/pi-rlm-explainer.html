System explainer · proposed design

pi-rlm turns a large problem into an inspectable program

Instead of putting an entire repository into one prompt, a controller receives a map of the material, writes small JavaScript cells, and spends a shared budget on the exact slices, models, agents, or recursive frames it needs.

TL;DR. The large input stays outside model context. A typed RlmProgram tells the runtime what goes in and what must come out. Model-authored JavaScript performs the adaptive search. Every host effect crosses a broker that authorizes, budgets, records, and can replay it.
Problem
Long inputs lose quality before they exceed the context window.
Approach
Keep data host-side; let a controller inspect and recursively query selected parts.
Tradeoff
More runtime machinery, latency, schemas, migrations, and failure modes.
Recommendation
Build the safe recursive core first; add opaque Pi agents only after approval and replay work.

The mental model: map, not cargo

Imagine a repository as cargo too large for one model request. Normal prompting loads the cargo into the model. pi-rlm gives the controller a variable catalog: names, types, descriptions, constraints, sizes, hashes, and bounded previews. The full values remain in snapshots.

A 300,000-token repository starts an RLM run. What enters the controller's first request?

Reveal the answer

Descriptors and bounded previews. Full values stay in immutable host snapshots. The controller requests slices explicitly, which makes context growth observable and enforceable.

The model chooses what to inspect next. The runtime decides whether that choice is legal, affordable, durable, and replayable.

Trace one run from question to answer

A route-security review shows why the runtime needs both model judgment and deterministic code.

Compile the program contract program/compiler.ts

The compiler validates names and JSON Schemas, resolves one profile, snapshots the matching route files, creates descriptors, and rejects collisions before model spend.

Controller inspects structure controller.ts

The first request contains instructions, descriptors, budget, DSL declarations, and a bounded trajectory. The controller writes a small cell to chunk route handlers by file.

One batch covers every route dsl/llm-batch.ts

llm.batch() validates all item keys and atomically reserves uncached work. If preflight fails, nothing launches and no call or attempt is consumed.

Code reduces semantic results interpreter/quickjs.ts

The model calls judge authorization semantics. JavaScript performs coverage checks, joins duplicates, and identifies any file without a result.

Typed answer commits persistence/journal.ts

answer({ findings }) must satisfy the declared schema. The payload is written and hashed before its commit event. Only the final result and artifact references return to the parent conversation.

Three contracts make the idea concrete

Use the tabs in order: the host declares the work, the guest performs it, and the trajectory records what happened. The copy button copies the visible tab.

const program = {
  version: 1,
  instructions: "Review every route for missing authorization.",
  inputs: {
    routes: {
      description: "TypeScript route handlers",
      source: { kind: "glob", pattern: "src/routes/**/*.ts" }
    }
  },
  outputs: {
    findings: { schema: { type: "array", items: findingSchema } }
  },
  profile: "code-review"
};
const chunks = await inputs.routes.chunks({
  targetTokens: 6000, maxChunks: 24
});
const reviews = await llm.batch({
  key: "review-all-routes",
  items: chunks.map(chunk => ({
    key: `review:${chunk.sha256}`,
    model: { tier: "small" }, context: chunk,
    prompt: "Return authorization findings as JSON."
  }))
});
answer({ findings: verifyCoverage(reviews, chunks) });

The rule worth remembering

Atomic rejection is a safety feature, not a partial failure.

If a batch cannot reserve the whole uncached group, no item launches and the rejected preflight consumes zero calls and attempts. Cache hits consume neither.

Replay changes what “state” means

A normal REPL can keep arbitrary objects in memory. pi-rlm cannot if a run must survive a process crash. Each cell receives a fresh context and a reconstructed, typed workspace. Closures, module state, timers, and prototype mutations are not durable state.

!
Opaque agents need approval every run. Delegation v1 cannot prove effective tools, mutation access, extensions, or network authority. “Do not edit” is guidance, not enforcement.

DSPy supplied abstractions, not the whole production runtime

DSPy's first-party RLM is unusually strong prior art: typed signatures, variable descriptors, interpreter ownership, ordered batched model calls, immutable history, typed submission, and fallback extraction. It is still experimental and is not the paper's reference implementation.

Glossary
Variable space
Host-backed values plus model-facing descriptors and previews. Separate from prompt token space.
Workspace
Serializable cross-cell state: JSON and tagged context or artifact handles.
Trajectory
Immutable per-iteration rationale, code, output preview, full reference, and typed error.
Unknown effect
A mutating call may have happened remotely, but no durable result was committed.
Fallback extractor
A separately versioned model call that tries to produce typed output after controller exhaustion.
